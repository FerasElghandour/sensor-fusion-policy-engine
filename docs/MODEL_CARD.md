# Model Card — model-based Entity Association

**v0.3 note:** this card covers `ai_entity_association.py` only — the model
that recommends which radar candidate matches a camera detection. As of the
official-challenge-text audit, a **second**, separate model,
`ai_compliance_risk.py`, was added specifically to give the AI a genuine
compliance-relevant role (essential outcome #1). See "Model Card — AI
Compliance-Risk Detector" at the bottom of this file. The two models are
architecturally independent: this one is advisory to *association*; the
other is advisory to *compliance enforcement*. Neither can permit, reject,
segregate, or downgrade anything on its own.

## Summary

A logistic-regression classifier that predicts whether a camera detection
and a radar detection describe the same real-world object. It is purely
advisory: `FusionEngine.run(..., use_ai_association=True)` uses it only to
choose which radar candidate to propose for fusion. The compliance decision
(`policy_engine.apply()`) and the confidence math
(`uncertainty_engine.fuse_confidence()`) run identically regardless of
whether the deterministic scorer or this model picked the candidate — the
model cannot permit, restrict, or leak anything on its own.

## Intended use

Recommending which synthetic radar candidate most likely matches a synthetic
camera detection, as an alternative to (not a replacement for) the
deterministic weighted scorer in `entity_association_engine.py`. Intended
only for this proof-of-concept's synthetic data; not validated on, or
intended for, real sensor data.

## Training data

100% synthetic, generated by `ai_entity_association.generate_training_examples()`.
Two overlapping Gaussian-noise generating processes — "true match" and "true
non-match" — produce 8 features each, with 5% of labels randomly flipped so
the classes overlap realistically rather than being trivially separable.
Default: 4,000 examples, seed 42, 80/20 train/holdout split.

| # | Feature | Description |
|---|---|---|
| 1 | `time_diff_s` | Absolute timestamp gap between the two observations (999.0 if either timestamp is missing) |
| 2 | `distance_diff_m` | Euclidean distance between reported locations (999.0 if either location is missing) |
| 3 | `direction_diff_deg` | Angular difference in reported heading, 0-180° (180 if either is missing) |
| 4 | `speed_plausibility_diff` | How far the radar's reported speed falls outside a plausible band for the camera's object class |
| 5 | `sensor_confidence` | Mean of the two observations' own `confidence_score` |
| 6 | `object_type_similarity` | 1 − normalized speed-band deviation (0.5 if speed is missing) |
| 7 | `data_completeness` | Fraction of 8 tracked fields (timestamps, locations, directions, speed, distance) that are non-null |
| 8 | `sensor_reliability` | Mean of fixed, synthetic per-platform reliability constants (camera 0.85, radar 0.92) |

## Model

`sklearn.linear_model.LogisticRegression` over `StandardScaler`-normalized
features, `max_iter=1000`. Chosen deliberately over a heavier model — every
prediction is explainable as an additive sum of `coefficient × scaled value`
per feature, with no separate explainability layer required.

## Measured performance (this run)

Trained via `get_default_model()` (seed 42, n=4000, 80/20 split):

- **Train accuracy: 0.9481**
- **Holdout accuracy: 0.9425**

Learned coefficients (on standardized features; sign shows direction of
influence, magnitude shows relative weight):

| Feature | Coefficient |
|---|---|
| `time_diff_s` | -0.577 |
| `distance_diff_m` | -0.773 |
| `direction_diff_deg` | -0.326 |
| `speed_plausibility_diff` | -0.454 |
| `sensor_confidence` | +0.302 |
| `object_type_similarity` | +1.079 |
| `data_completeness` | +0.422 |
| `sensor_reliability` | -0.002 |
| intercept | -0.238 |

`object_type_similarity` dominates (largest positive coefficient); the four
"gap" features (time/distance/direction/speed) all correctly push toward
non-match as they grow, as expected. `sensor_reliability` carries almost no
weight — it varies little across the synthetic training distribution
(uniform 0.80-0.92), so the model correctly learned not to rely on it.

The historical system-level figures in older drafts used a different source/metric version.
Use [VALIDATION.md](VALIDATION.md) and its saved cases for the current system comparison.
Do not mix the model-only holdout accuracy above with end-to-end association F1.

## Explainability

Every prediction returns a `MatchPrediction` with `match_probability`,
`predicted_match`, and up to 4 human-readable lines, e.g.:

```
Object-type consistency (1.00) pushed toward MATCH, weight +1.68
Location distance (0.21) pushed toward MATCH, weight +0.68
```

computed as `coefficient × scaled_feature_value`, ranked by absolute
contribution — no separate "explain" model or approximation is needed.

## Known limitations

- Trained on a hand-authored synthetic distribution that does not perfectly
  match the adversarial mission generator's exact distribution of gaps and
  noise — this is why the model doesn't strictly beat the deterministic
  baseline (B) on every run (see `reports/failure_analysis.md` for the
  specific conditions where it disagrees most, e.g. `missing_timestamps`).
- `sensor_reliability` is a fixed constant per sensor type in this POC, not
  learned from real calibration history — it's structurally present in the
  feature vector for future extension, not because it currently carries
  much signal.
- Never validated against real sensor data, and not intended to be — see the
  "no real sensors" constraint in ARCHITECTURE.md.
- The model can be uncertain (`match_probability` near 0.5); see
  `reports/failure_analysis.md`, "Scenarios where the AI model was
  uncertain," for concrete examples from the last benchmark run.

## Retraining

`EntityAssociationModel().train(n_samples=..., seed=..., test_fraction=...)`
retrains from scratch; `get_default_model()` is a cached singleton (seed 42)
used everywhere else for reproducibility. There is no persisted model
artifact on disk — the model is small enough (8 features, logistic
regression) to retrain in well under a second at process start.

# Model Card — AI Compliance-Risk Detector

## Summary

A second, separate logistic-regression classifier (`ai_compliance_risk.py`)
that scores a single ingested item's *metadata pattern* for compliance
risk — not whether it matches another sensor's reading, but whether its
classification, provenance, or domain metadata looks suspicious. It is
purely advisory, exactly like the association model: `ComplianceEngine.inspect()`
always runs the deterministic `policy_engine` afterward, and the AI's
`risk_probability` can only make one specific, policy-author-written rule
condition (`requires_ai_risk_at_least` in `policy_schema.py`) eligible to
match. That rule (`AI_HIGH_RISK_REVIEW` in `policies/default_policy.yaml`)
is deliberately written to only ever *escalate* an otherwise-PERMIT
decision to REQUIRE_REVIEW — it runs at priority 90, after every
classification/domain rule, so it can never override or loosen a
higher-priority deterministic REJECT/SEGREGATE/DOWNGRADE decision.

## Intended use

Flagging incoming camera or radar metadata that looks like it might carry a
classification, provenance, or cross-domain problem the deterministic,
field-value-based rules don't directly check for (e.g. an item whose
classification/domain/release-authority *markings are simply absent*, not
wrong). Advisory only. Synthetic data only; not validated on real sensor
data.

## Training data

100% synthetic, `ai_compliance_risk.generate_training_examples()`. Two
generating processes ("risky metadata" / "clean metadata") over the 10
features below, mostly Bernoulli draws at different risk-appropriate
probabilities, with 5% label noise. Default: 4,000 examples, seed 43,
80/20 split.

| # | Feature | Risk category it detects |
|---|---|---|
| 1 | `missing_classification_marking` | Missing classification markings |
| 2 | `missing_domain_of_origin` | Missing domain of origin |
| 3 | `missing_release_authority` | Missing release authority |
| 4 | `classification_field_mismatch` | Classification inconsistent with field contents |
| 5 | `suspicious_classification_downgrade` | Suspicious classification downgrade |
| 6 | `provenance_gap` | Provenance gaps |
| 7 | `unexpected_transformation_history` | Unexpected transformation history |
| 8 | `source_destination_domain_conflict` | Source/destination domain conflict |
| 9 | `restricted_field_pattern_in_transformed_record` | Restricted fields hidden inside transformed records |
| 10 | `metadata_sensor_type_mismatch` | Metadata patterns inconsistent with known sensor type |

Features 1-3 read three new `DataItem` boolean flags
(`classification_marking_present`, `domain_of_origin_marking_present`,
`release_authority_marking_present`, all default `True`) added specifically
so "the marking is absent" is representable independent of "the marking has
a specific (wrong) value." Feature 4 reuses the same field-sensitivity-
mismatch logic as `policy_engine.py`'s `MISCLASSIFIED_FIELD` rule — the AI
and the deterministic rule are asking a related question about the same
underlying signal, from two different angles.

## Model

`sklearn.linear_model.LogisticRegression` over `StandardScaler`-normalized
features — the same architecture as the association model, for the same
reason: every prediction is explainable as `coefficient × scaled value`,
ranked by contribution, with no separate explainability layer.

## Output

`ComplianceRiskAssessment`: `risk_probability` (0-1), `risk_categories`
(names of features that crossed the 0.5 detection threshold),
`contributing_factors` (top-4 weighted features, same style as the
association model's explanation), `confidence`, and a plain-English
`explanation`. Structurally, this type has **no field for an enforcement
action** — it cannot represent a decision to permit, restrict, segregate,
reject, or downgrade, only a risk opinion (verified by
`tests/test_ai_compliance_risk.py::test_risk_assessment_has_no_enforcement_action_field`).

## Measured performance

Holdout accuracy on the synthetic training distribution: see
`tests/test_ai_compliance_risk.py::test_model_trains_and_beats_a_coin_flip`
(asserts > 0.6; typically ~0.9+ on a fresh run — re-run
`ComplianceRiskModel().train()` for the exact current number, not hardcoded
here since it is not a claim this project treats as load-bearing evidence).

At the 1,000-mission benchmark level (`reports/benchmark_summary.csv`):
`missing_metadata_detection_rate` for the compliant approaches was measured
at less than 1.0 on the most recent run — a real, disclosed gap: the
`missing_metadata_markings` adversarial condition only forces 3 of the 10
risk features; the other 7 vary with the rest of the item's otherwise-
normal state, so the AI_HIGH_RISK_REVIEW threshold (0.85) is not always
crossed. `false_compliance_alert_rate` (false escalations on fully clean,
untagged missions) was measured at 0.0 on the same run. See
`reports/failure_analysis.md` for the exact numbers from the most recent
run — this card does not restate them so it can't drift out of sync.

## Known limitations

- The 0.85 escalation threshold is a fixed constant, not tuned against a
  cost model (false-review cost vs. missed-risk cost) — it was chosen
  empirically to avoid false-escalating well-formed synthetic test data,
  not derived from any operational requirement.
- Features 1-3 depend on the new marking-presence flags being set
  correctly by whatever produces a `DataItem` — a real sensor integration
  would need to map its own metadata-completeness signals onto these three
  flags; nothing does that mapping today.
- Like the association model, this is trained on a hand-authored synthetic
  distribution, not validated against real metadata-quality problems.

## Retraining

`ComplianceRiskModel().train(n_samples=..., seed=..., test_fraction=...)`;
`get_default_risk_model()` is a cached singleton (seed 43) used everywhere
else for reproducibility. No persisted model artifact — retrains in well
under a second.
